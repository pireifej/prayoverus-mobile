Please update the existing prayer-request posting interface.

The current flow already works:
1. The user opens the prayer request screen.
2. They enter prayer text.
3. They submit it.
4. The frontend calls the backend moderation function before posting.
5. The backend checks for issues such as money requests, violence, self-harm, etc., and returns JSON.

Do not replace the existing posting logic or create mock data.

When checking the prayer content, call:

POST /checkPrayerContent

Send:

{
  "requestText": "<the user's original prayer text>",
  "userId": "<the authenticated user's ID>"
}

The userId is required because moderation emails need to identify the user. Make sure the authenticated user's actual ID is passed to the check function.

If the moderation response includes suggested wording, for example:

{
  "flagged": true,
  "caringNote": "...",
  "suggestedWording": "...",
  "suggestion": "...",
  "isHardBlock": false,
  "allowPostAsWritten": true
}

Then update the interface as follows:

- Display the caring note in a supportive information panel.
- Display the suggested alternative as a clearly labeled, read-only preview titled “Suggested wording” or “Suggested prayer.”
- Prefer suggestedWording when available.
- Fall back to suggestion if suggestedWording is missing.
- Keep the user's original wording available as the other choice.
- Give the user two clear choices:
  - “Use suggested prayer”
  - “Post as written”
- When the user confirms either choice, immediately post the selected wording.
- Do not run /checkPrayerContent again after the user selects the suggested wording.
- The suggested wording must not be editable.
- Advisory flags must not automatically block posting.
- Only prevent posting when the backend explicitly returns a hard block or the actual posting request fails.
- For non-flagged requests, preserve the current normal posting flow unchanged.
- Disable the relevant buttons while moderation or posting is in progress to prevent duplicate submissions.
- Preserve the existing loading, success, and error states.
- Do not expose raw moderation JSON to the user.
- Keep the design accessible, readable, mobile-friendly, and consistent with the existing app styling.
